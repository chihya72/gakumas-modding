## 1. 最终目标

AB + Runtime 的目标不是把任意外来模型强行改造成一副学马体型，也不是把外来网格重新绑定到学马骨架。

目标路线是：

1. 作者把来源模型整理为合格的 **T-pose**。
2. 保留来源模型自己的完整骨架层级、骨长、身体比例、蒙皮权重和 bindpose。
3. 用人体语义把学马骨架的最终动作映射到来源代理骨架。
4. 学马原骨架继续负责游戏动画、IK、关节修正和游戏侧驱动器。
5. 来源网格只跟随来源代理骨架，不把来源权重直接套到学马骨的位置上。
6. 来源专有的裙摆、尾巴、头发、饰品等骨骼，再按明确的归属规则接物理或保持为硬骨。

这条路线如果完成，可以消除“为了转移权重而把外来网格完美贴到学马身体”和“把每根来源骨移动到学马关节位置”这两类主要工作。它不能消除 T-pose 整理、骨骼语义确认、头颈接口处理和物理配置。

## 2. 不再改变的 T-pose 约束

### 2.1 正式协议永久只接受 T-pose

这是产品和协议约束，不再规划 Runtime 直接接收 A-pose：

- AB 导出器的正式输入必须是 T-pose。
- Runtime 动画桥只处理以 T-pose 为静止基准的来源骨架。
- 检查器发现来源模型不是合格 T-pose 时必须阻止出包，不能只写警告后继续。
- 不能增加“允许 A-pose 继续导出”或“Runtime 自动猜测静止姿势差”的开关。

这里要求的是同一套可验证的 T-pose 框架，包括肩、手臂、手掌、手指、左右对称和骨骼滚转方向。骨长和人物比例不要求与学马一致。

### 2.2 未来唯一允许研究的是出包前自动 A→T

未来可以单独测试 Unity 实验中的自动 A→T 烘焙思路，但它只能是制作工具：

```text
原始 A-pose
  → 出包前自动烘焙工具
  → 合格 T-pose
  → T-pose 硬闸门再次检查
  → AB 导出
  → Runtime
```

自动烘焙必须同时处理：

- 骨架静止姿势；
- 网格顶点；
- bindpose；
- 手指等完整人体链；
- 形状保真和蒙皮自洽验证。

只旋转骨骼、不处理顶点，或者只重算 bindpose、不处理网格，都不是可接受的 A→T。自动工具没有通过验证前，作者仍然手动摆 T-pose。

即使未来自动 A→T 成功，AB 包和 Runtime 接收到的仍然是 T-pose；正式协议不会因此放宽为直接支持 A-pose。

## 3. 必须区分的三条路线

### 3.1 远端最新发布版的混合骨架路线

当前发布路线会尽量复用学马现有骨，把来源权重所引用的人体骨接到学马骨上，再为一部分额外骨创建节点。

它的优点是改动小，能直接使用游戏动画和现有运行时组件；缺点是来源 bindpose、来源权重和学马骨的静止空间必须足够接近。来源和学马骨长、关节位置、局部轴或静止姿势差异很大时，网格就会被拉扯。

因此，在这条现有路线里，“尽量贴合学马身体和骨架”仍然有实际意义。

### 3.2 本地实验的协议 2 静态代理路线

本地 `ModRuntime.cpp` 已经有实验协议 2 和 `BuildSourceProxyBoneArray()`：

- sidecar 声明的每根骨都新建，不复用学马同名骨；
- 原版 Renderer 仍被使用，但其 `bones` 数组换成来源代理骨；
- 网格继续使用来源权重和来源 bindpose；
- 协议验证失败时关闭该网格替换，不静默退回旧混合路径；
- 当前明确是 `rest-only`，动画和物理被主动关闭。

这说明“建一套独立代理骨架”和“让来源网格继续吃来源权重”已经不是纯设想。但当前实现仍只是实验能力，不是发布版功能。

### 3.3 最终来源代理骨架路线

最终路线在协议 2 静态代理上增加每帧动画桥、完整来源 Transform 树、头颈接口、生命周期管理和明确的双骨架组件归属。

只有这条路线完成后，才能正式声称：来源模型不需要为了权重转移而完美贴合学马身体，也不需要逐骨对齐到学马骨长和关节位置。

## 4. 当前实机到底证明了什么

### 4.1 已经证明的部分

> ⚠️ 2026-08-16 晚更正：这次测试用的包**不是 Claymore**，是串进来的 `kth_ss202`（一套学马
> 约定的服装 rig，连根骨都叫 `Reference`）。机制、证据和闸门见
> [事实文档 §4.5](ab-consolidated-facts-and-evidence-2026-08-16.md)。下面第三条已划掉。

静态代理测试中，来源网格成功进入游戏并停在 T-pose。这个结果证明：

- 来源网格、来源权重、来源 bindpose 和独立来源骨架可以形成闭环；
- 同名人体骨没有必要直接复用学马 Transform；
- ~~来源身体比例可以保留~~ —— **未证明**。`kth_ss202` 的比例和骨架约定本来就是学马的，
  这条要用真的外来模型（Claymore T-pose 包）重测；
- 静态代理路径值得继续做动画桥。

身体停在 T-pose 是因为实验 Runtime 明确关闭了动画桥，不是学马把模型自动摆成了 T-pose。

### 4.2 没有证明的部分

这次成功不能证明：

- Runtime 可以直接接受 A-pose；
- 52 根人体骨的动画桥已经可用；
- 学马 IK、姿势驱动器和摇物已经正确接入来源代理；
- 多角色性能已经合格；
- 游戏脸、头发和来源身体已经自动接合。

测试使用的是已经被 Unity 工具烘焙为 T-pose 的产物，不是原始 A-pose。

### 4.3 A 包没有生效的真实原因

后来制作的 A-pose 协议 2 包没有替换网格，只替换了材质。直接原因不是“A-pose 一定被游戏拒绝”，而是 sidecar 只记录了 Renderer 的蒙皮骨数组，没有记录完整 Transform 树。

该包声明 `Hips` 为来源 `rootBone`，但 `Hips` 不在那份蒙皮骨数组中。运行时找不到根骨后按协议 2 的关闭式规则返回失败，所以出现 `meshApplied=0`、`materialApplied=1`。

因此，这次 A 包没有产生可用于评价 A-pose 形变的实机结果。尽管如此，根据本文第 2 节的决定，正式路线也不会继续尝试 Runtime 直吃 A-pose。

### 4.4 旧混合实验和协议缺字段是两个独立问题

旧的 A-pose 混合骨架实验确实应用了网格，但来源静止空间与学马骨差异很大：已有记录测得 `LeftShoulder` 约 177.5°、`Hips` 约 177.2°，平均位移约 22.61 cm。

这说明来源权重直接指向学马实时骨会发生严重拉扯。把 sidecar 改成完整 Transform 树，只能解决“代理骨建不全”；真正消除这种拉扯的是完整来源代理骨架加动画坐标转换。两者不能混为一个问题。

## 5. 学马 70 根基础骨与来源代理骨的关系

530 套学马身体共有 70 根基础骨：

- 52 根 Unity Humanoid 人体骨；
- 14 根 `*_H` 关节修正骨；
- `Pelvis`；
- `Reference`；
- `LeftBust1_S`、`RightBust1_S`。

这 70 根说明了学马动画和组件可能引用哪些基础语义，但不等于每个来源模型必须被强行改造成同名、同层级的 70 根骨。

正确关系是：

- **学马骨架**：游戏动作和游戏组件的控制侧。
- **来源代理骨架**：来源模型自己的完整 Transform 树。
- **人体语义映射**：把学马需要传递的动作通道接到来源对应节点。

第一版至少要可靠覆盖 52 根人体语义，并明确声明来源顶层、Renderer 的 `rootBone`、整体移动通道，以及保留游戏脸/头发时使用的 `HeadSocket`。

其余 18 根不能统一粗暴处理：

- 来源已有等价扭转骨或胸骨时，可以认领；
- 只作为挂点且插入后不改变蒙皮时，可以按需要新建；
- 没有对应功能时可以明确留空；
- 只有确认需要转移的影响，才做显式权重转换。

“节点存在”不等于“关节修正已经生效”。强行给来源模型补齐 14 根 `*_H`，却没有对应权重和求解器，只会得到一张看似 70/70 的假完成表。

## 6. 协议 2 必须先拆开完整层级与蒙皮骨数组

当前一个 `bones` 数组同时承担了两件不同的事：

1. 描述要创建的来源层级；
2. 描述 Renderer 权重索引所对应的骨数组。

这在 `rootBone`、无权重父节点和挂点不属于蒙皮骨数组时必然失败。新协议至少应分成：

| 字段 | 作用 |
|---|---|
| `transforms` | 完整来源 Transform 树，包含无权重祖先、辅助节点和挂点 |
| `skinBones` | 指向 `transforms` 的索引；顺序必须与权重和 bindpose 一致 |
| `bindposes` | 与 `skinBones` 一一对应的来源 bindpose |
| `semanticMap` | 学马人体语义到来源 Transform 的明确映射 |
| `rootTransform` | 来源代理层级顶层 |
| `rootBone` | SkinnedMeshRenderer 使用的根骨，可不在蒙皮骨数组中 |
| `HeadSocket` | 保留游戏脸/头发时的接合节点及位置、旋转、缩放修正 |

运行时应先按 `transforms` 创建完整树，再用 `skinBones` 组装传给 Renderer 的骨数组。任何索引越界、父级缺失、根骨缺失、bindpose 数量不符或必要语义缺失都必须停止该 Renderer 的应用，并写明错误原因。

## 7. 动画桥的职责与边界

动画桥不是复制同名骨的当前旋转。它需要保存学马骨和来源骨各自的 T-pose 静止矩阵，把学马骨相对自身静止姿势的变化转换到来源骨的坐标系中。

它要解决的是：

- 两套骨架骨长不同；
- 关节位置不同；
- 局部轴向不同；
- 父级层次可能不同；
- Hips 的位移和整体尺度需要单独规则。

它不负责把 A-pose 当作合法输入，也不负责自动猜错失的人体语义。

正确的每帧顺序目标是：

```text
游戏 Animator
  → 游戏 IK、Quartz、关节修正
  → 把最终人体动作写到来源代理骨
  → 来源专有骨物理
  → 渲染
```

游戏现有 ActorSwing、QuartzDriver 的更新窗口可以作为挂接时机的参照，但仍需用一次实机跟踪确认：写回确实晚于游戏人体动画和必要修正、早于来源物理与渲染。

## 8. 两套骨架并存时必须规定谁能写哪根骨

在接物理前要先锁定以下归属：

| 对象 | 最终写入者 |
|---|---|
| 学马 52 根人体骨 | 游戏 Animator、IK、游戏姿势驱动器 |
| 来源代理中的 52 根对应人体骨 | 动画桥 |
| 来源硬质附加骨 | 父级继承或显式挂点 |
| 来源裙摆、袖子、尾巴、头发等动态骨 | 来源侧物理解算器 |
| 学马 `*_H`、Bust 等游戏修正骨 | 游戏对应驱动器 |
| 来源扭转骨、胸骨 | 动画桥或来源求解器二选一 |
| 学马 `Head` 的**世界位置** | 动画桥（HeadSocket 吸附，2026-08-16 起） |
| 学马 `Head` 的**旋转** | 游戏（Animator + 点头/视线修正）——**不要碰** |
| 来源代理骨的**位置/骨长** | 谁都不写（只写世界旋转，来源骨长因此原样保留） |
| 渲染器的材质数组 | 运行时（每次应用克隆游戏 `m_bdy`，见 §4.11） |
| 代理容器的生命周期 | 运行时：建新的之前销毁同父级下所有 `__gmi_source_proxy_rest__*` |

硬规则是：

> 同一个实际 Transform 每帧只能有一个最终写入者；同一个动作语义只能有一条传递路径。

2026-08-16 补一条细化：**归属的粒度是「通道」，不是「Transform」。** 学马 `Head` 现在是
旋转归游戏（Animator + 点头/视线修正）、位置归动画桥，两者不冲突且都必须保留——
把它整根划给任一方都会坏事（划给游戏＝头回到原版高度，划给桥＝脸失去视线修正）。
后面接物理时按同样粒度写归属，别再用整根骨当单位。

碰撞体可优先放在游戏身体侧，来源动态骨放在代理侧，但需要实测游戏组件能否稳定引用另一套层级中的碰撞体。不能等到所有摇物装完后才决定归属。

## 9. 头和身体为什么会分离

静态 T-pose 截图中，来源身体停在代理骨架上，学马脸和头发仍跟随原游戏骨架与动画。两套骨架没有动画桥，也没有经过校准的头部挂点，所以头和身体分离是必然结果，不是 T-pose 本身造成的。

已有测量显示来源 `Neck→Head` 距离约为学马的 1.50 倍，说明头颈接口存在显著比例差；这个数不能直接推导出头部宽、高、深都统一为 1.50 倍。

如果保留学马脸和头发，`HeadSocket` 的位置、旋转和大小校准是必须步骤，不是可选微调。至少要测：

- 颈部接缝位置和半径；
- 头部宽、高、深；
- 眼间距和面部中心；
- 头发根部与头骨的包围关系。

如果未来允许使用完整来源头，则是另一条脸、表情和头发替换路线，不能假装与“保留学马脸”共用同一套验收。

## 10. 从 Unity SDK 实验中真正值得搬的东西

### 10.1 可以直接借鉴思想和数据的部分

1. **人体语义识别的分层方法**：格式元数据优先，结构推断其次，不确定时作者确认。
2. **T-pose 检查方法**：检查人体骨相对标准姿势的偏差；AB 正式流程只使用检查和硬闸门。
3. **动画坐标转换的验证方法**：比较同一动作意图下两套骨架的关节方向和末端位置。
4. **来源组件搬运思想**：来源格式确实携带物理/驱动信息时，逐实例读取并转换，不用中位数猜参数。
5. **学马驱动器清单和取值范围**：给作者按骨骼组选择真实学马驱动器，并对字段和引用做关闭式校验。
6. **摇物链几何特征**：链方向、锚点、影响顶点范围、身体占比等用于候选排序和分组证据。
7. **碰撞体和 Renderer 的处理经验**：独立碰撞笼、多个 Renderer、独立附件和状态切换需要单独协议表达。

### 10.2 不能原样搬过来的部分

- Unity Humanoid 的 Avatar 构建器不能在 Blender 或游戏 Runtime 中原样调用；AB 需要保存映射结果和自己的验证逻辑。
- Unity C# 组件不能直接塞进 AB 包；需要转换为 sidecar 数据和 C++ Runtime 的实际组件安装。
- 来源物理如果在转成 FBX 前已经丢失，AB 不能凭空恢复原刚体、Joint、DynamicBone 或 PhysBone 参数。
- Unity 实验里某个来源包的成功参数不能当成所有 MMD、VRM、Biped、Rigify 或乱码骨架的通用真值。

## 11. Blender 插件最终应呈现的作者流程

当 Runtime 核心路线验证成立后，插件按三层识别：

1. **来源格式有明确说明**：直接读取 PMX/MMD、VRM、Unity Humanoid、DynamicBone、PhysBone 等可用元数据，转换为统一语义和来源组件记录。
2. **没有明确说明**：根据骨架层级、左右位置、骨长、关节方向和网格权重推断候选；Humanoid 的判断思路放在这一层。
3. **存在歧义**：在图形界面展示候选、置信度和理由，让作者确认。不能安静地把不认识的骨焊到 Hips，也不能只靠英语名字猜。

对不能映射为人体骨的节点，插件先按连通链、共同锚点和影响网格区域形成骨骼组。例如一条尾巴从根到末端形成一组，而不是让作者逐根点几十次。

每组再让作者选择：

- 套用学马哪一种可用驱动器；
- 作为硬骨；
- 作为普通附加物；
- 根据来源弹簧或合成弹簧新增；
- 明确忽略。

当前 Blender 插件的 4 类预设只是通用弹簧参数类别，不等于学马的 12 类原生驱动器。未来可以把 12 类真实驱动器列给作者，但只有 Runtime 已实现该组件、必要引用能补齐、当前骨骼组满足前提时才能启用；其余必须说明缺什么并置灰。

## 12. 验收标准不能再用“看起来没爆炸”

每个关键阶段都需要三类证据。

### 12.1 蒙皮自洽

比较来源静止顶点与按来源权重、当前代理骨矩阵和来源 bindpose 重建后的顶点，至少记录平均值、P95 和最大位移；人体影响区域与额外骨影响区域分别统计。

### 12.2 形状保真

把最终出包网格与作者原始网格放在同一世界空间比较，记录平均值、P95 和最大位移。

如果某阶段宣称没有修改几何，差异应接近导入和浮点误差，不能以厘米级误差通过。Blender 到 Unity 因分裂顶点造成索引变化时，应使用 Unity 导入基准、稳定的顶点来源编号或表面距离，而不是强行按顶点序号比较。

### 12.3 固定渲染对照

保存同一动作、同一相机、同一缩放下的正面和侧面截图，和原始来源或基准模型同帧对照；最好增加透明叠图或轮廓差异。

只有三者同时成立，才能写“通过”。日志出现“应用成功”只代表代码路径执行，不代表模型正确。

同时记录 1、3、5 个可见角色的性能。每个角色可能新增约数百个 Transform，并每帧转换 52 条人体通道，所以必须记录创建耗时、内存、每帧 CPU 的 P50/P95 和物理开关前后的差异。

  **这是闸门：孤儿骨不会再静默生效。**

**待实机的五个场景**（每个跑完读 `duplicateProxyNames` 和 `Destroyed stale source proxy containers`）：
换装 / 切角色（销毁重建，注意 `[N]` 索引会复用）/ Mod 开关 OFF→ON / 包原地更新后重载 /

## 14. 现在能承诺和不能承诺的效果

### 14.1 路线完成后可以实现

- 保留来源骨长、身体比例、完整来源权重和 bindpose；

> ⚠️ **本节已作废（2026-08-17 晚）。** whole-object 违反「作者只开 Blender」这条基调：
> 带组件的 prefab **UnityPy 造不出来**（搬 nodes 会碎、清 typetree 被 Unity 拒、留旧 typetree
> 写新字节原生崩），必须 Unity 出包。而 whole-object 的全部价值就在那些组件上。
> 现行路线见 [`ab-target-rig-route-2026-08-17.md`](ab-target-rig-route-2026-08-17.md)。
> 下面保留作对照组记录——**§4.13–§4.15 量到的事实仍然有效**，作废的是"该走这条路"这个结论。

本文前面 14 节写的是**两副骨架 + 手写动画桥**。2026-08-17 实机证明了另一条更短的路，
本节的结论**优先于前面所有关于动画桥的实施安排**：

> `replaceWholeObject`（manifest 本来就有）把整个 body prefab 交给游戏，游戏用**我们的骨架**
> 建 Humanoid Avatar，重定向由 Unity 引擎自己完成。**动画、跳舞实机正常，没有桥。**

代价与收益的重新定价：

| | 两副骨架（§7–§9 那套） | 一副骨架（whole-object） |
|---|---|---|
| 动画重定向 | 手写，已实现 | **Unity 自己做** |
| 头挂点 / Hips 位移 | 各自单独实现 | 不存在 |
| 碰撞体点击 / 道具挂点 / 取景 | 每项单独补，今晚逐项确认都欠着 | 骨架只有一副，天然一致 |
| 出包要求 | 宽松 | **必须满足 body prefab 的全部隐式契约** |

**代价整体从运行时挪到了出包侧，而且是可枚举的**：`IkRigger` 那批必需节点已经解决（见
事实文档 §4.13）；剩下的按同样方式逐条补。

**一条转向后必须遵守的规矩**：两副骨架时期「决定不做」的每一个步骤，都要**重新定价一遍**。
因为桥吸收了轴向差、静止差、比例差，很多东西当时确实不必做；一副骨架下没有吸收者，同一个
属性的定价可能完全相反。已经踩到的一例：源骨轴向对齐当时被判为"破坏性且无必要"，现在是
麦克风朝向的唯一解（事实文档 §4.14）。

因此：**§7 动画桥、§8 归属表里桥相关的行、第 3/4/5/7 步的桥部分，转为「对照组，勿再投入」**。
代码不删（它是唯一能动的对照），但新问题不要再在桥上修。

### 15.2 已知的三个缺口（按优先级）

1. **`*_H` 命名断层（唯一的结构性缺陷）**
   `TwistAdopter` 认领源模型自带扭转骨、**不改名**（游戏运行时按组件类型收集，成立）；
   `QuartzDriverRigger` **按名字**找 `LeftArm_H` 等再挂驱动器，于是 16 个必备驱动器一个没装。
   两边各自都对，拼起来漏。**这就是「自建骨架要满足 70 根基础骨」这个判断的真正落点**：
   对游戏是功能不能少，对工具链是**名字不能少**。
   两条修法二选一：认领时改名，或让 `QuartzDriverRigger` 吃 `TwistAdopter` 的认领表。

2. **摇物参数是合成的，不是真值**
   源模型没有 `_S` 命名，链是按几何分类认出来的（27 条 / 78 根）。参数按预设合成，
   而同一角色不同衣服的 stiffness/pendulum 能差 100 倍——「会动」和「动得对」是两件事。
   真值来源见事实文档（原版 bundle 内嵌 typetree，别猜偏移）。

3. **麦克风残差**：轴向对齐后仍差一点。轴向已排除，下一个嫌疑是 socket 的局部位姿
   （我们的手骨尺寸与原版不同，位移分量不随旋转修正而正确）。
