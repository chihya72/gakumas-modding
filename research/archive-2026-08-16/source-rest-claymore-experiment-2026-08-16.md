# Claymore 外部模型“保留源骨架”实验记录（2026-08-16）

## 1. 结论先行

以 `Avatar_Girl_Claymore_MarionetteNew.fbx` 为样本，已经完成三轮离线受控实验。

结论是：

1. **这个模型的来源人体骨能够被识别。** Unity 成功建立 Humanoid Avatar，自动映射 52 根人体骨；现有 Biped 命名预设也能覆盖同一量级的人体骨。因此，本次失败不是“完全不知道谁是谁”。
2. **当前 AB v2 的 lossless graft 并没有完整保留来源骨架。** 它保留来源权重、来源 bindpose 和来源专有骨，但凡骨名能匹配学马骨，就直接让网格使用学马活体骨的 Transform，来源骨自己的静止位置、骨长和局部坐标系不会成为一套独立骨架留在运行时。
3. **直接把来源 bindpose 接到学马活体骨上会严重变形。** 原始 A 姿势直接接入时，`Body` 网格的平均静止位移约 37.7 cm，95% 分位约 101.1 cm，最大约 146.6 cm。
4. **T-pose 是必要条件，但不是充分条件。** Unity 把双臂与手指烘焙到标准 T-pose 后，平均位移降到约 21.9 cm；再把 40 根受驱动骨和头骨的局部轴向校正后，平均位移降到约 12.8 cm。结果明显改善，但裙摆仍整片飞离，不能使用。
5. **真正“不逐骨对齐也保留原权重”的路线，需要一套运行时来源代理骨架。** 不能继续把来源权重直接指向学马骨。运行时必须创建完整来源骨架，由学马骨的动画变化去驱动这套代理骨架，再让网格继续使用来源 bindpose 和来源权重。

因此，本实验否定的是“当前 graft 加上 T-pose 就等于完整来源骨架”这一说法；它没有否定“通过新增来源代理骨架实现完整保留”的未来路线。

## 3. 为什么这能模拟当前 Runtime

当前 v2 路径的关键行为在 `gakumas-mod-runtime/src/runtime/ModRuntime.cpp`：

- `BuildHybridBoneArray()` 遇到与学马骨同名的 sidecar 骨时，直接把 `hybridBones[index]` 指向原版活体骨（当前文件约 `2847-2851`）。
- 只有找不到同名原版骨时，才按 sidecar 的局部位置、旋转和缩放创建新骨（约 `2852-2871`）。
- 网格继续使用 mod/source bindpose，并把上述混合骨数组交给原版 Renderer（约 `3171-3180`）。

因此，当前所谓混合骨架实际是：

```text
能匹配的人体骨 = 学马活体骨 Transform
匹配不到的来源专有骨 = 按来源局部变换创建，挂到混合父骨下面
网格 = 来源权重 + 来源 bindpose
```

实验对每个顶点计算相同的线性蒙皮关系：

```text
运行时骨矩阵 × 来源 bindpose × 来源顶点
```

这不是把两个截图凭肉眼比较，而是在静止状态直接检查蒙皮恒等式是否成立。

## 5. T-pose 为什么有效，但为什么还不够

本样本的手臂是明显 A-pose。Unity Humanoid 测得上臂与标准 T 的偏差约 67° 至 69°。如果只换骨的静止旋转、不同时改顶点和 bindpose，会让骨架与网格分处两个静止姿势；本轮使用的是 SDK 已验证的完整烘焙，即顶点和 bindpose 一起重算。

这一步确实把整体平均误差从 37.7 cm 降到 21.9 cm，证明 T-pose 问题真实存在。

但 T-pose 只规定主要关节的姿势方向，并不保证以下内容相同：

- 每个关节的世界位置；
- 上臂、前臂、躯干和腿的长度；
- 骨骼 roll；
- 每根骨的完整局部三轴；
- 不同骨架中的父子层级和中间扭转骨；
- 裙摆、头发等专有骨相对父骨所使用的坐标系。

第三轮已经把 40 根最关键驱动骨的轴向也校过，但 50 根可比较人体骨的静止关节位置仍平均相差 3.16 cm，最大 7.17 cm。未覆盖或无法仅靠该步骤统一的躯干、肩、脚趾等骨仍有很大的静止轴向差。例如 Spine/Spine1/Spine2 的完整骨坐标系仍相差约 112° 至 116°。

所以“符合 T-pose 框架”不能只解释成双臂水平。若要直接复用学马 Transform，它实际要求来源骨的完整静止矩阵足够接近学马；这已经接近另一种形式的逐骨对齐。

## 6. 裙摆为什么是最大失败项

第三轮中，按“有该骨权重的顶点平均位移”排序，最严重的骨几乎全部是来源裙摆或下摆骨：

- `Bone_SkirtF11_L`：约 0.933 m。
- `Bone_SkirtC05_L`：约 0.918 m。
- `Bone_SkirtC04_L`：约 0.759 m。
- `Bone_SkirtF03_L`：约 0.737 m。
- `Bone_SkirtF04_L`：约 0.695 m。

这并不是因为来源权重丢了；恰恰相反，来源权重和 bindpose 都还在。错误来自这些骨的运行时 Transform 已经不再处于它们的来源静止空间。

因此，“权重完整保留”和“骨架完整保留”必须分开描述：

- 当前 v2 能保证权重索引不越界、不丢影响、bindpose 数量对应，这可以称为**数据无损 graft**。
- 当前 v2 对匹配骨复用学马 Transform，不能称为**端到端保留来源骨架**。

## 7. 本轮得到的正确架构方向

要实现用户希望的效果：作者不逐骨把模型贴到学马体型，来源权重继续可用，来源裙摆/头发骨也保留原层级——运行时需要从“混合骨数组”升级成“来源代理骨架”。

建议的数据流：

```text
来源格式的明确元数据 / Unity Humanoid / 结构与权重推断
                    ↓
作者确认人体语义映射
                    ↓
完整来源静止骨架 + 来源权重 + 来源 bindpose
                    ↓
Runtime 创建完整来源代理骨架（匹配骨也创建，不直接借用学马骨）
                    ↓
读取学马骨相对其静止状态的动画变化
                    ↓
把变化转换后写到来源代理骨；保留来源骨长、关节位置和专有骨层级
                    ↓
来源网格继续绑定来源代理骨 + 来源 bindpose
```

这里“外部骨骼 -> 中间状态 -> 学马骨骼”更准确的方向应是：

```text
学马动画变化 -> 人体语义中间层 -> 来源代理骨架
```

网格不能直接改绑到学马骨；它应该始终跟来源代理骨架绑定。人体语义中间层只负责把动画意图送过去。

来源专有骨再分三种处理：

- 硬骨：保持来源层级，随父骨刚性运动。
- 附加物：保持来源层级，由明确的附件规则控制显示或挂点。
- 弹簧/学马驱动器骨：作者按连通链分组后选择学马驱动类别或新弹簧参数。

## 8. 下一轮应该验证什么

本轮没有直接生成进游戏 AB 包，因为静止态蒙皮恒等式已经失败；把已知拉爆的数据打包进游戏只会重复同一个结论。

下一轮应做最小“来源代理骨架”原型，而不是继续调 bindpose：

1. 在 Unity 编辑器先创建完整来源代理骨架。
2. 人体匹配骨不直接换成学马骨，保留来源局部位置、骨长和父子层级。
3. 用学马骨的“相对静止旋转变化”驱动来源代理骨，先只验证躯干、双臂和双腿。
4. 让一条来源裙摆链保持在来源父骨下，验证静止态为零误差、动作时不脱体。
5. 与 Unity Humanoid 对同一组姿势作画面对照。
6. 编辑器原型通过后，再把同一算法移入 Runtime，最后才出游戏包。

需要单独实测、现在不能承诺的内容：

- 不同身材比例下，学马动作驱动来源骨架是否自然；
- 肩、髋、手指、脚掌和扭转骨的旋转分配；
- Root/Hips 位移与身高缩放；
- 原版姿势驱动器和来源代理骨之间的执行顺序；
- 来源裙摆、头发等物理骨如何接学马 12 类驱动器；
- 表情、独立 Renderer、透明/穿脱状态和材质的运行时接入。

## 10. 本轮最终判定

| 命题 | 判定 |
|---|---|
| 这个外来 Biped 骨架能否识别人体语义 | **能**；Unity Humanoid 自动映射有效，52 根 |
| 当前 v2 是否已完整保留来源人体骨架 | **否**；同名骨直接复用学马 Transform |
| 只要来源权重可用，当前 v2 是否无需骨架对齐 | **否**；来源权重可用不代表来源静止空间与学马骨一致 |
| A-pose 是否应转 T-pose | **是，本样本收益显著**；但只是必要步骤 |
| T-pose 后是否可直接接学马骨 | **否**；关节位置、完整轴向、层级仍不一致 |
| 未来是否可能避免逐骨贴合并保留来源权重 | **可能**；前提是实现并实测来源代理骨架与动画桥，而不是沿用当前直接复用学马骨的 graft |
