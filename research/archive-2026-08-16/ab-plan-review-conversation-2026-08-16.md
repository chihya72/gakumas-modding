## 3. codex 的回应与结论

codex 接受 §2.3 的第 1、2、3、5、6、7 条，部分接受第 4 条。其中三处需要记录：

### 3.1 codex 的修正是对的：空引用不能只加 `return false`

【已核实】codex 指出修法不能只在 `ModRuntime.cpp:779` 后 `return false`，因为
`AddComponentByClass` 在 **743 行**就执行了，早于骨引用循环（775）。直接返回会留下
半初始化组件，而 il2cpp 侧没有干净的移除路径。

补充两点（本轮新发现）：

- **这个坑现在已经存在**：748–750 行在 setting 建不出来时就是 AddComponent 之后才 return。
- `slot()` lambda（**756 行**）对 int/float/vector 字段同样是「没这个字段就忽略这一项」，
  fail-closed 必须连它一起，否则驱动器照样带默认值静默跑。

正确顺序：

```text
1. FindClassByName 两个类（现有）
2. 预检：所有 bones 能 resolve + 字段存在；所有 int/float/vec 字段名存在
3. INV-1 占用闸门（现有 728–741，移到这里）
4. 全过才 AddComponent → EnsureReferenceField → 写值
5. 可选 allowMissingReferences，默认关
```

约 30 行重排，不是三行。

### 3.2 codex 的两处过度设计（评审提出，后被作者答案整个作废）

- **八项作者成本基线过重**：其中「失败归类为骨架/权重/物理/材质/生命周期」需要判断，
  不同时间记出来不可比。
- **codex 第 1 条与第 5 条是同一份 schema 写了两遍**（`组编号/成员骨/…` 与
  `groupId/memberBones/…`）。

### 3.3 codex 保留小回归集的意见成立

不建大型标注集，但保留几个固定样本（已知 MMD、名字打乱、左右歧义、非标准脊椎），
只检查「正确候选是否排在前面 / 歧义时是否要求确认 / 有无静默错误 / 旧样本是否回归」，
不算总体召回率。评审补充：不必凑四套真骨架，拿一套真 rig 用脚本派生打乱名字和对称歧义
两个变体即可。

## 4. 作者澄清（本轮最重要的部分）

以下全部是【作者澄清】，权威，推翻了评审双方的多项推断。

### 4.1 真实痛点排序

1. **权重最麻烦**——手部调参稍不注意手指变长/变短/扭曲畸形；**A-pose→T-pose 后肩膀变小崩坏**
2. **贴图 / 描边 / 光照 / 阴影 / 材质**：已有一整套自建模拟流程，「大体是对的」，但希望有
   真实的「外部贴图 → 学马贴图」转换方法，一键完成
3. **骨架**：几乎每个 mod 一开始都绑错，但很明显，调试几次就能判断对

### 4.2 三条关键事实

- **A→T 是作者手工在 Blender 里转的，肩膀崩坏在 Blender 里就看得见。**
  不是导出/游戏侧问题。
- **作者不是用源权重，是从原版身体转移权重。** 因此必须先在 Blender 世界坐标里把网格贴上，
  贴不准手指就变形。**贴合方式：手工挪 + 缩放。**
- **手指的骨映射本身是对的**，问题在贴合精度。

### 4.3 关于「留空的骨」

作者原话：不知道为什么这些骨骼没自动匹配上，**是指它们被排除在 8 张源骨→游戏骨预设之外**，
只能走自动匹配模式。fuyuko 表单底部显示「还有 57 个骨没指定目标（留空=交给自动判断）」。

chisaki 泳装（MMD）案例：裙子几十根摇物链骨（`Dress_1_1` … `Dress_9_16`，每根 0.03% 权重），
**作者手动点了几十次「跟裙摆」**。原话：「某些 MMD 模型给裙子建了几十根摇物链骨骼，
在学马里根本不是这样建的，我是要一根一根全部手动设置吗？」

### 4.4 不能靠名字

作者明确：「万一别的骨是日语呢？万一是中文呢？万一是乱码呢？」——
任何基于名字前缀/关键词的方案都不接受。

### 4.5 作者从没用过 driver 路径

作者不知道 `_form_driver_categories()` / `native_driver` 是什么。

### 4.6 作者最终诉求（原话转述）

> 做一个分区自动匹配，按照骨架本身的形状、结构、原模型骨架中自带的驱动器等等，把原模型和
> 学马模型的通用骨匹配起来；然后给其他不能直接匹配的骨按分组分类，比如一根尾巴从前到后
> 全部分为一组；然后在菜单里让作者选，是套用学马的哪一类驱动器，如果都不要，再选要作为
> 硬骨、还是附加物、还是根据弹簧新增。

## 6. 本轮从产物里读出来的证据

来源：`mod-workspace/mods/work/hmsz-cstm-0059_body_dress-2219-TEST/`（fuyuko，SCSP 源，
383 骨 / 298 顶点组 / 123 带权重 → 目标 156 骨）

### 6.1 72 根源骨静默塌进 Hips

【已核实】导出的 `sourceRigRemap` 共 272 条映射，其中 **72 根指向 Hips**：
整套 `HAIR_Back_*`（32 根，四条链）、`HAIR_Side_*`、`acce_Bow_*`、`Belt_L_*`、`Key_R_*`、
`Chain_R_*`、`Bag_R_*`。

sidecar 里这两条**没有任何字段区分**：

```text
"Hips": "Hips"                 ← 真的认出来了
"HAIR_Back_R_E3": "Hips"       ← 认不出来，焊上去了
```

后果：它们不进 `unmapped`（`operators.py:792`）、不报错、表单上看不出来。作者说的
「不知道为什么没自动匹配上」，实质是**它们没有匹配失败，它们静默成功了**。

### 6.2 源自带的扭转/辅助骨被塌成一根

【已核实】

```text
LeftShoulder ← LeftShoulder + LeftShoulder_rot + LeftClavicle
LeftArm      ← LeftArm + LeftArm1_rot + LeftArm2_rot + LeftArm3_rot
LeftForeArm  ← LeftElbow + LeftForeArm + LeftForeArm_rot
```

权重统计佐证：`LeftShoulder` 吃了 **4213** 个顶点，`LeftArm` **4311**——肩膀和上臂几乎
一样重，这在原版身上不该发生（锁骨的活被肩膀干了）。

注意：这与 §4.2「肩膀崩坏在 Blender 里就可见」**不冲突**，是两个独立问题。
既有记录（`joint-collapse-needs-vanilla-helper-rig`）指出 rip 普遍自带扭转骨，正确做法是
**认领**（接到 `*_Roll_H` 一类）而不是塌；`bone_remap_presets.json` 里 MMD 的腕捩/手捩
已经会落到 `*_Roll_H`，**SCSP 的 `*_rot` 没有这条规则**。

### 6.3 手指映射是干净的

【已核实】`LeftHandThumb1 → LeftHandThumb1` 一路 1:1，五指十五根全没塌。

### 6.4 前缀批量能力已存在，但只在 JSON 不在 UI

【已核实】

- `build_accessory_physics_remap()` 的 `overrides` 参数按**最长前缀匹配**
  （`core.py:2742` docstring、`core.py:2792` `override_for()`）
- 入口 `gmi_physics_override_file` 存在于 UI「高级」面板（`ui.py:228`）
- 但表单那一列走 `_form_physics_overrides()`（`operators.py:709`），**按精确骨名收集**

fuyuko 的 `inputs/physics-override.json` 里就是一行 `"Skirt": "follow_skirt"` 盖掉 30 根。
chisaki 工作区**没有 inputs/ 目录**——作者一直在表单里逐根点。

（注：这条能力**不构成解法**，见 §5 第 4 行，名字可能是任意语言。记录在此是因为它说明
UI 与 core 的能力落差，以及 core 侧「组级写入」的管道本来就通。）

### 6.5 现有分组也是按名字的

【已核实】`group_key()`（`core.py:2782`）：

```python
return re.sub(r"(?:left|right|_l|_r)(?=_|$)", "", name.lower())
```

剥 left/right 当组名。日语/中文/乱码全废。代码里已有 ponytail 注释承认它是启发式。

### 6.6 Preserve Volume 从未启用

【已核实】全仓 grep `use_deform_preserve_volume` / `preserve_volume` **零命中**。

假设（**未验证**）：A→T 是大角度旋转（肩到臂约 40–50°），线性蒙皮下肩部 50/50 权重顶点
被挤扁，`Apply as Rest Pose` 把挤扁**永久烘进几何**，之后再好的权重也救不回。Blender
自带解法是 Armature 修改器的 Preserve Volume（双四元数蒙皮）。若成立，P7 从「移植 CATS +
写姿势求解器」缩成**烘焙前设一个 flag**。双四元数有自身鼓包问题，须先量再决定。

验证需要**转 T-pose 之前**的 A-pose 文件（作者提供的 `authoring - 副本.blend` 已转完）。

### 6.7 仓库里没有任何 fit / align 工具

【已核实】只有 `tools/report_joint_alignment.py` 这把尺子，没有 fitter。

## 7. 作者诉求与真实成本 vs 现有能力

| 作者要的（§4.6） | 现状 |
|---|---|
| 通用骨按结构匹配 | **半个**：`topology_map.py` 按拓扑猜核心骨，但只 15 根，且**只挂在 Unity 实验入口，AB 主路径没调它** |
| 按结构分组（尾巴/裙/发） | **没有**。`group_key()` 是名字规则（§6.5） |
| 组 → 硬骨 | 有，`rigid` |
| 组 → 附加物（跟随现有骨/链） | 有，`follow_nearest` / `follow_skirt` / `follow:<骨>` |
| 组 → 新建弹簧 | 有，`integrate` |
| 组 → 套用学马某类 driver | 代码有，**引用补不齐**，缺引用时空跑（`ModRuntime.cpp:779`） |
| 读原模型自带的驱动器 | **读不到**，见下 |

### 7.1 结构分组是可做的，数据已经在手上

不看名字只剩两样，而**两样都已经传进函数了**：

- 父子层级：`parent_by_name`（`operators.py:770`）
- 骨的位置：`source_bones`

`rigid_parent()`（`core.py:2771`）已经在做「顺着父链往上走，找到这根装饰骨最终挂在哪根
游戏骨下」——**锚点计算是现成的**，只是算完就扔了，只拿来当兜底目标。

```text
锚点 = rigid_parent(骨)      → 挂在哪根游戏骨下
链   = 沿父子走到分叉为止    → 一条链是一个整体
组   = 同锚点的链聚在一起
```

**已知天花板**：光按锚点太粗。fuyuko 那 72 根装饰骨**全部锚在 Hips**（裙子 + 腰带 +
钥匙 + 包 + 整头后发会被归成一组）。要分开得再加一层链根位置聚类（裙子的链根在胯周围
围成一圈，包的根是孤立点）。

评审建议：**先只做锚点 + 链，粗的**。72 根 → 12 条链 → 1 组，就算归错也是「一组拆成两组」，
远好过现在 72 行；碰到拆不开的再加聚类。这条要写成明确的已知天花板，不装作够用。

### 7.2 「原模型自带的驱动器」在 Blender 里已经没了

MMD 的刚体/Joint、VRM 的 spring bone、DynamicBone 参数是**源文件里的数据**，不是骨架的
一部分。`mmd_tools` 直接开 PMX 会保留刚体（空物体 + 约束），但中间过一道 FBX 物理就整个丢，
blend 里再也读不出来。

架构含义：要用源物理，必须**在导入之前读原始文件**，插件得多一个「从 .pmx / .vrm 读」的
入口，不能指望从 blend 里挖。

**未决**：chisaki 那个模型是 pmx 直接导入还是过了 FBX——作者尚未回答。这决定源物理是
「现在就能做」还是「得先加导入入口」。

### 7.3 「给整组选学马 driver」能列，多数选不了

12 类 driver 引用要求各异：有的要服装自己的 `*_O` 偏移骨，有的要左右成对，有的要特定宿主。
分组不难，难的是选完之后自动补齐引用；补不齐现在是 warning + 空引用继续跑，画面上就是
部件完全不动而日志一切正常。

诚实做法：菜单里全列出来，缺引用的置灰并写明缺什么，别让作者选到看起来成功的空壳。
这一项卡的是 driver 引用，不是分组，应单独排。

### 7.4 网格贴合：文档谈的「对齐」和作者做的「对齐」是两回事

这一条是作者两大痛点之一（§4.1 第 1 条的另一半），**分量重于 §7.1–§7.3 的任何一项**，
但原文档 §14 的 P0–P9 里没有一项对着它，仓库里也没有任何 fit 工具（§6.7）。

原文档 §5 整节论证「lossless graft 保留源权重和源 bindpose，所以作者不必把两副**骨架**的
世界坐标逐根重合」。数学上成立。但作者要对齐的不是骨：

```text
文档谈的对齐：源骨   ↔ 游戏骨       逐根位置重合    → lossless 确实不需要
作者做的对齐：源网格 ↔ 原版身体网格  世界坐标贴合    → 权重转移的前提，必须做
```

因为作者**不用源权重**，他把原版身体的权重转移到新网格上。权重转移按几何邻近找对应，
所以两个网格必须先在世界坐标里贴上；贴不准就转移到错的顶点——手指变长、变短、扭曲畸形。
当前贴合方式是**手工挪 + 缩放**（【作者澄清】）。

三点必须写清楚，免得下一位评审又读成「lossless 免对齐有个例外」：

1. **不是例外，是两个不同的对象。** §5 的结论对骨成立，对网格根本没谈。原文档需要补一句：
   免对齐只在直接用源权重时成立；走权重转移就必须贴合，且贴合精度直接决定手部质量。
2. **如果哪天改成直接用源权重（真 lossless），贴合就不需要了**——但那要求源权重本身可用。
   SCSP / MMD 源的权重能不能直接用在学马身体上，是一个**未验证**的问题，没验之前不能把
   「改用源权重」当成绕过贴合的方案。
3. **`ab-alignment-manual-plus-gate` 里「自动对齐已放弃（两次产废品）」说的是关节对齐（骨），
   跟网格贴合不是同一件事**，不能拿它当「网格贴合也别自动化」的依据。这两件事被混为一谈过，
   §9 第 5 问要按这个区分重新提。
