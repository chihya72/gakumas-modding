# 9. 常见问题与排错

按现象查。每条都给**根因**和**去哪修**，不只是症状。

## 9.1 换模后完全没有描边

**根因**：学马仕的描边读**顶点 COLOR**。新网格缺 COLOR，被默认白色冲掉 → 描边消失。

**修**（三个部件的来源不一样）：

- **body**：步骤③的 **`描边颜色`** 默认「取自基础色」，逐顶点从 t0 采样，所以**步骤②必须先填 t0**；
  想最保守选「黑色常量」，想按材质槽区分选「按材质预设」。这条路径不需要参考模型；
- **hair**：描边的 LUT 行 / 宽度 / rim mask 是从**带权重参考网格最近邻拷贝**的，
  **导出 hair 时必须保留参考模型**，否则插件直接报「参考网格没有 COLOR 属性」；
  再按发色明度选对 **`发型描边色档`**（见 [[7-发型与发饰]]）；
- **hairprop**：按材质槽写常量，不走参考拷贝，金属件把材质槽标 `metal` 即可。

这不是 ini / 法线问题，别往那边查。

## 9.2 透明件渲染成黑块

**根因**：透明区的 RGB 留成了纯黑，游戏在边缘把黑色混进来 → 发黑。

**修**：

- 保留 alpha，只把 RGB **向外扩**（alpha-bleed），不要把透明区 RGB 留黑；
- DDS 用带 alpha 的 **BC7 / BC3** 格式；
- **不要**为了省事把 t0 改成不透明。

见 [[8-透明材质（原生co）]]。

## 9.3 暗面出现不属于这件衣服的彩色图案

**根因**：只换了 t0，没换 t4。暗面继续读原服装的 `sdw`。

**修**：t4 要和 t0 **同 UV、同图案**，只是更暗 / 轻微偏色。没有现成 t4 就用「按材质生成 t1/t4」或勾中性 t1/t4。见 [[5-步骤②-材质与贴图]]。

## 9.4 换发型后出现蓝紫色斑纹 / 旧发色泄漏

**根因**：hair 的 t1.A 写高了，换过 UV 的新发型会错采到原角色的高光贴图。

**修**：自定义 UV 的发型把 **t1.A 设 0**。没有现成 t1 时用「按材质生成」的头发预设即可。见 [[7-发型与发饰]]。

## 9.5 暗光 / 特殊场景下全身颜色错乱

这是 3DMigoto 路线特有的老问题（贴图按寄存器硬绑，shader 变体一换槽位就重排），**AB 路线不存在**——贴图按 `rendererName + materialSlot + property` 语义覆盖，不吃寄存器重排。

若你用的还是旧的 3DMigoto mod 包，那是另一套东西，本 wiki 不再覆盖。

## 9.6 导出被拒：某个承重关节没拿到权重

**根因**：21 个承重关节（Hips / Spine / Spine1 / Neck / Head / 左右 Shoulder-Arm-ForeArm-Hand 与 UpLeg-Leg-Foot-ToeBase）里有一根没权重。多半是**该源骨没在骨骼映射表里指到游戏骨**，少数情况是模型那块本来就没刷权重。

**修**：

- 回步骤③的骨骼映射表，把被点名的关节对应的源骨指对；
- 若模型该处确实无权重，回建模软件补。

这道闸门是故意拦你的：旧版这种情况会**导出成功、进游戏才发现整只手钉在 Spine1**。见 [[6-步骤③-导出AB bundle]] 6.2。

## 9.7 进游戏模型错位 / 沉到地下

**根因**：作者模型没和参考身体对齐，或没应用变换。权重虽然是你自己的，但游戏骨架在固定的空间位置上。

**修**：摆到参考身体位置、接近尺寸、同为 T-pose，再 `Ctrl+A` 应用缩放 / 旋转。见 [[4-步骤①-准备配置档]]。

## 9.8 导出报错：配置档没有透明部件

**根因**：材质槽选了「原生 co」，但当前配置档来自一套没有透明件的服装。

**修**：把该材质槽改回「不透明」，或换一个**含透明件的抓帧**重新生成配置档。见 [[8-透明材质（原生co）]]。

## 9.9 插件提示匹配到多个候选 / 匹配错了对象

**根因**：几套服装长得太像，插件拿不准该用哪套，或自动选错了游戏对象。

**修**：

- 按插件提示手动指定具体 Body；
- 命令行按 3DMigoto 顶部 Draw 编号强制指定：
  ```powershell
  python tools\extract_frame_profile.py <FrameAnalysis目录> <输出目录> --component body --draw 335
  ```

见 [[4-步骤①-准备配置档]]。

## 9.10 飘带 / 裙摆 / 花边不动或乱甩

**根因**：装饰骨的物理策略选错了。这类骨头**名字和位置都决定不了它该怎么动**——源作者常把腰饰绑在胸骨、把裙边花边绑在大腿上，实测按位置猜只有 1/3 命中。

**修**：在步骤③骨骼映射表的第二列逐条改。当前推荐：

- 裙边需要和原版裙摆精确同步：选「跟裙摆」；
- 独立悬垂的飘带/蝴蝶结：可选「自建摇物链」。2026-08-11
  `hmsz-fuyuko-icu` 已画面级确认正常摆动；插件会按原版类别决定是否真的挂链，飘带通常只用
  逐骨动态组件，裙类才使用环形碰撞链；
- 扣子、徽章等硬质配件：选「刚性跟父骨」。

自建物理仍要目视验收幅度和穿插。若只是直接热 ON 一个新增了摇物结构的包，要重新进入场景，
因为新骨/链只在 prefab 与角色初始化阶段注册。见 [[6-步骤③-导出AB bundle]] 6.1。

**注意策略键是前缀最长匹配，不是子串**：骨名是 `Spine_Bow_L_A0`，写 `Bow` 匹配不上，要写
`Spine_Bow`。

裙内侧问题三角要关描边，加入 `GMI_NO_OUTLINE` 顶点组。

## 9.11 面板还是旧英文按钮

装的是旧版。**卸载旧插件 → 关闭 Blender → 重开 → 装新版 ZIP。** 见 [[1-环境准备与安装]]。

## 9.12 发型 mod 装上后只有一半生效（换了发饰但发型回到原版，或反过来）

**根因**：包里只有一个 renderer 规则。发型和发饰是同一件头饰的两个 renderer，
运行时只处理包里声明了的那个，另一个原样不动。

**查**：`gakumas-mod\mod-plugin.log` 里这一行是判据——

```text
SkinnedMeshRenderer replacement finished: ... originalRenderers=2 replacementRenderers=2 pairs=1
```

`pairs=1` 就是只处理了一个 renderer；正确的合并包是 **`pairs=2`**。
再往上翻还能看到具体处理了哪个：`originalRenderer="Geo_HairProp"`。

**修**：**激活「发型」网格**，在导出框「发饰对象」里选上发饰，重新导出。
激活发饰去导出现在会被直接拒绝。见 [[7-发型与发饰]] 7.3。

## 9.13 模板补丁失败，提示 `submesh count changed`

**根因**：作者网格的材质槽数没能归并到目标段数。发型 / 发饰目标各 1 段，身体是 1 段、2 段
或（少数服装）3 段。正常情况下导出会自动归并，前提是这些槽**共用同一张贴图**。

**修**：把作者网格的材质收拢到共用一张 atlas；身体上若确实需要透明件，
把对应槽标「原生 co」并选一个带 `bdyco` 的目标服装（见 [[8-透明材质（原生co）]]）。

## 9.14 导出报错：`材质槽 N 缺少 t0 基础色贴图`

**根因**：某个材质槽的 `渲染材质` 是「原生 co」，而「原生 co / m_bdyco」区的 **t0 是空的**。
co 的 t0 **不会**回退借用 body 的 t0——它用透明件自己的 UV，借过来只会是错的。

**修**：补上 co 自己的 t0（带 alpha）；这件衣服本来就不需要透明件的话，把该槽改回「不透明」。

> **插件 0.9.3 之前**还有另一种触发：目标服装原版有 3 段时（`cstm-0119` 全系列等 18 套），
> 即使你一个 co 槽都没标，也会被那个你根本没用到的空段拽去要 co 的 t0。升级到 1.0.0 即可。

## 9.15 日志里看不到任何替换过程

默认 `logLevel=error`，只记录错误。在 `<游戏目录>\gakumas-mod\config.json` 写：

```json
{ "modManagerUi": true, "logLevel": "info" }
```

重启游戏后 `mod-plugin.log` 会有完整 trace：`Registered replacement candidate` →
`Replacement hit` → `Mesh diagnostics before/after` → `Applied ... skeleton graft` →
`Applied material texture` → `replacement finished`。排查完记得改回 `"error"`。

## 9.16 更新 Runtime 后旧 Mod 全部失效

**根因**：新版 Runtime 会核对骨架 sidecar 的 `runtimeProtocol` 与 `buildId`。旧插件导出的包没有
协议字段，或包内文件来自不同构建；继续套用可能把不兼容的骨架数据写进角色，所以 Runtime 会
拒绝完整替换。这是预期的兼容性保护，不是随机失效。

**修**：从原 `.blend` 用当前 Blender 插件重新导出整个 Mod。不要只改 `mod.json`，也不要手填
协议字段冒充新包；bundle、sidecar 和 manifest 必须来自同一次导出。

## 9.17 管理页开启后主页没生效，进一次换装页才生效

2026-08-12 之前的 Runtime 在开关发生时若场景里没有目标 Renderer，会写
`hotInstances=0` 后丢掉这次即时应用。当前 Runtime 已改为延迟队列：正常日志应先出现
`Deferred hot reapply queued`，角色/Renderer 生命周期到来后再出现
`Deferred hot reapply satisfied`。其中 `applied=0 alreadyPatched=1` 表示资源加载路径已经先
完成替换，延迟路径只确认结果并清队列，不是失败。

若仍复现：先确认游戏目录里的 `xinput1_3.dll` 是最新构建，把 `logLevel` 设为 `info`，按“管理页
ON → 直接回主页”的顺序复现并保留完整 `mod-plugin.log`。改变了新增摇物骨/链结构时仍需重进场景。

---

没覆盖到的问题：保留 `bundle-src\` 与 runtime 的 `gakumas-mod\mod-plugin.log`，对照对应专题页排查。日志会写明命中了哪个 renderer、替换了几个目标。原理级记录在仓库 `research/` 目录。
